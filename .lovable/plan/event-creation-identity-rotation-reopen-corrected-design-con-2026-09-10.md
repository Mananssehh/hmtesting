# Event Creation / Identity / Rotation / Reopen — Corrected Design Contract (rev 2, no implementation)

Revised after independent review. All seven corrections applied. Nothing implemented, deployed, migrated or rotated.

## 1. Writer inventory (unchanged evidence)

RLS policies: `DJs can create events` (INSERT, client-supplied code), `DJs manage their own events` (UPDATE, role PUBLIC, no WITH CHECK), `DJs delete their own events` (DELETE, PUBLIC), `events_select_owner`, `events_select_member`.

## 2. Enforcement mechanism (Correction 1)

The client security boundary is **column privileges**, not role-name detection. No `current_user` / `session_user` bypass exists anywhere in this design.

```
REVOKE INSERT, UPDATE ON public.events FROM PUBLIC, anon, authenticated;
REVOKE DELETE ON public.events FROM PUBLIC, anon;
GRANT  DELETE ON public.events TO authenticated;            -- Correction 4
GRANT  SELECT ON public.events TO authenticated;
GRANT  UPDATE (name, venue, dj_name, allow_explicit, require_approval,
               cooldown_seconds, rules_text) ON public.events TO authenticated;
-- service_role keeps ALL
```

Policies: drop `DJs can create events` and the old UPDATE policy; create `events_update_settings` (TO authenticated, USING and WITH CHECK `dj_id = auth.uid()`). **Keep `DJs delete their own events`** (Correction 4), retargeted `TO authenticated`.

The trigger enforces **caller-independent structural invariants** only:

1. `id`, `dj_id`, `created_at` can never change (any caller, including definer functions and service_role).
2. A transition from ended state to any live/open state is rejected **unless `room_code` differs from OLD in the same statement**.
3. Any new `room_code` must match `^[ABCDEFGHJKLMNPQRSTUVWXYZ23456789]{6}$`.
4. Rotation codes are generated by a private generator, never accepted from a caller: `private.generate_room_code()` (definer, `extensions.gen_random_bytes`, EXECUTE revoked from PUBLIC/anon/authenticated). Where the trigger detects a rotation-requiring transition and the RPC did not already set a fresh code, the trigger calls the generator itself.

Result for a raw PostgREST client: no INSERT privilege at all; no UPDATE privilege on `id`, `dj_id`, `room_code`, `created_at`, `is_active`, `requests_status`, `ended_at`, `archived_at`; therefore no reopen, no code choice, no alternative lifecycle field. The trigger is a structural backstop against privileged mistakes, not the client boundary.

## 3. Trigger ordering (Correction 2)

Consolidate. `set_event_ended_at` and `sync_event_active` are **dropped** and their logic folded into a single `BEFORE INSERT OR UPDATE` trigger `events_lifecycle_guard` on `public.events`. No other BEFORE trigger remains on the table, so ordering is unambiguous. Execution inside the one function, in order:

1. Identity invariants (`id`, `dj_id`, `created_at`) — raise on change.
2. Lifecycle derivation: `requests_status='ended'` → `ended_at := coalesce(OLD.ended_at, now())`, `is_active := false`; leaving `ended` → `ended_at := NULL`, `is_active := true`.
3. Rotation rule: if step 2 produced an ended→live transition and `NEW.room_code = OLD.room_code`, set `NEW.room_code := private.generate_room_code()` (retry loop lives in the RPC; trigger-level collisions surface as `unique_violation` to the caller).
4. Room-code format assertion on the final `NEW.room_code`.

## 4. RPC contracts

Common: `SECURITY DEFINER`, `SET search_path=''`, fully qualified, no dynamic SQL, `SELECT … FOR UPDATE` on the event row, generic `{"ok":false,"reason":"unavailable"}` for not-found and not-owner, and `REVOKE EXECUTE ON FUNCTION … FROM PUBLIC, anon; GRANT EXECUTE TO authenticated` **in the same transaction as CREATE FUNCTION**.

`rotate_event_room_code(_event_id uuid, _idempotency_key uuid) → jsonb` (Correction 3) — owner-only; lock row; look up `private.event_rotation_idempotency(event_id, idempotency_key PK, room_code, created_at)`; on hit return the recorded code unchanged; otherwise generate via `private.generate_room_code()`, retry on `unique_violation` up to 10 then `could_not_allocate_room_code`, assert new ≠ current, write the event and the idempotency record in the same transaction, return `{ok, event_id, room_code}`. Two different deliberate keys rotate twice. Abuse limit: 5 successful rotations per event per rolling hour via `rate_limit_logs` (`endpoint='rotate_event_room_code'`) → `rate_limited`. The frontend generates one key per confirmed rotation action and reuses it on retry.

`reopen_event(_event_id uuid) → jsonb` — owner-only; `FOR UPDATE` **before** reading lifecycle state, so a concurrent second call observes the reopened row and returns `{ok:true, outcome:'already_open', room_code}` without rotating. If genuinely ended: one UPDATE sets `requests_status='live'`, `archived_at=NULL` and a freshly generated `room_code`; the guard trigger derives `is_active=true`, `ended_at=NULL` and enforces that the code actually changed. No instant exists where the event is live under the old code.

`end_event(_event_id uuid, _archive boolean default false) → jsonb` (Correction 5, option (a)) — owner-only; sets `requests_status='ended'` and, when `_archive` is true, `archived_at = now()`. The guard derives `ended_at`/`is_active`. No separate `archive_event` RPC; the matrix wording "end/archive" means this single RPC with the flag.

`set_requests_status(_event_id uuid, _status text) → jsonb` — owner-only pause/resume within a non-ended event; refuses `'ended'` (use `end_event`) and refuses any reopen from ended (use `reopen_event`). Lifecycle authority is single-sourced in these four RPCs.

## 5. Creation enforcement

Exactly §2. `create_event` already requires an authenticated `dj`-role caller, forces `dj_id := auth.uid()`, and never accepts a client code. Dependencies on direct INSERT: none in `src/`, none in Edge Functions, none in Vitest; `supabase/d5b-staged/*` unaffected.

## 6. Frontend impact

`src/pages/DJDashboard.tsx` and `src/pages/DJEventManage.tsx` must call `reopen_event` / `end_event` / `set_requests_status` / `rotate_event_room_code`, adopt the returned code, refetch the event, generate a rotation idempotency key per confirmed action, and show a confirmation dialog warning that old links and printed QR codes stop working. A manual "Rotate code" action is added. This requires a frontend publish and triggers the agreed bundle-verification rule.

## 7. Rotation safeguards

Membership, requests, votes, tips and Bridge rows are keyed by `event_id` and survive rotation. Broken by rotation: printed QR/short links, guests refreshing an old `/join?code=` URL (generic unavailable), stale dashboard tabs, Bridge snapshot output (self-heals), and Stripe `success_url`/`cancel_url` built from `room_code` in `tip-create-checkout:250` (payment still succeeds; tip keyed by `event_id`).

Preconditions before any live rotation: no request/vote in the last 15 minutes; no Bridge heartbeat in the last 15 minutes; no unexpired pending Checkout Session; DJ informed and ready to replace links/QR; old→new state recorded as hashes only. No alias for an old code.

## 8. Ended events (review-confirmed, unchanged)

Accepted conditional on enforcement proving: `join_event_by_code` rejects ended/inactive events generically; no direct client field update can reactivate them; every reopen path rotates atomically before going live; no alternative RPC can reopen them; D5A blocks nonmember lookup. The four already-ended events therefore need no rotation.

## 9. Staged rollout (Correction 6)

- **Stage 1 — additive only:** `private.generate_room_code()`, the idempotency table, and the four RPCs. No trigger change, no grant/policy change. Old frontend keeps working unchanged. Tests only.
- **Stage 2 — frontend:** publish the RPC-based dashboard, rotation confirmation and idempotency keys; verify the new bundle hash. Direct PATCH is still permitted, so cached tabs still work.
- **Observation window:** the agreed frontend observation window elapses before Stage 3.
- **Stage 3 — enforcement (single step):** drop `set_event_ended_at`/`sync_event_active`, install `events_lifecycle_guard`, and apply the REVOKE/GRANT/policy changes together. Cached pre-Stage-2 tabs now fail End/Reopen with a permission error and a toast — no silent change, no partial lifecycle state.
- **Stage 4 — bypass verification:** re-run every probe as DJ and as anon, plus the closure tests in §11.
- **Stage 5 — per-event remediation:** only after separate, explicit, per-event human approval.

## 11. Tests

Behavioural (isolated Postgres): direct INSERT denied (anon + DJ); `create_event` succeeds for a DJ, denied for guest/non-DJ; UPDATE denied on each of `id`, `dj_id`, `room_code`, `created_at`, `is_active`, `requests_status`, `ended_at`, `archived_at`; allowed settings UPDATE still succeeds; owner DELETE still succeeds and non-owner DELETE denied; raw PATCH cannot reopen; `reopen_event` rotates before live in one statement; repeated reopen returns `already_open` with the same code; two concurrent reopens produce one new code; rotation owner-only; same event + same idempotency key returns the identical code; two distinct keys rotate twice; concurrent rotations preserve uniqueness; new ≠ old; forced 10-collision path fails cleanly with no partial write; `end_event(_archive=>true)` sets `archived_at`; participants/requests/votes/tips still attached after rotation; ended weak code cannot join; reopened event accepts only the new code; banned guests still blocked; D5A privacy and D5B index/trigger/RPC unchanged; Bridge snapshot, tip checkout, archive/analytics still resolve.

Privilege/policy closure (post-deployment, catalog-level): `information_schema.role_table_grants` and `pg_class.relacl` show **no** table-level INSERT or UPDATE on `public.events` for PUBLIC, `anon`, `authenticated` or any role they inherit; `information_schema.column_privileges` lists exactly the seven approved settings columns as updateable and no others; `pg_policies` for `public.events` contains exactly the intended set with no leftover permissive policy (policies OR together, so a stale one reopens access); every new function shows PUBLIC EXECUTE revoked, granted in the same transaction as its creation; `private.generate_room_code()` is not executable by `anon`/`authenticated`.

Each stage ends with typecheck, full Vitest, Deno tests and a production build. Stage 2 adds Vitest coverage for reopen/rotate handlers, idempotency-key generation and the stale-code warning.

## 12. Rollback — forward-only (Correction 7)

- Stage 1 additive objects: droppable.
- Stage 2 frontend: the previous bundle may be republished **only before Stage 3 enforcement**. After enforcement it is not a safe rollback.
- Enforcement: **never** restore direct client-selected room-code creation; **never** restore direct protected lifecycle/identity updates. If the new frontend misbehaves after Stage 3, the database stays closed and the fix is forward in the RPC or frontend.
- Ending a live event: reversible only through `reopen_event`, which rotates.
- Rotated weak codes are never restored.

- **IP-header probe:** separate approval and deployment track under the previously stated conditions (≥256-bit token, temporary Edge secret, never committed or logged, temporary `verify_jwt=false` scoped to the probe, uniform auth failures, POST + `Cache-Control: no-store`, no database client, deleted with its config entry and secret immediately after verification). Not deployed under this contract.
